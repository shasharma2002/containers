# Cargo tracking and reporting

Tracks containers and bills of lading with the shipping lines, and turns the
results into one Excel report you can send to the people who need it.

```
bl_list.xlsx  ->  track_all.py  ->  containers.json / events.json
(commercial sheet)                  errors.json / shipments.json
                                             |
                                    generate_report.py
                                             |
                             output/cargo_tracking_report.xlsx
```

Two layers that do not depend on each other. The tracking layer talks to
carriers and writes JSON. The reporting layer only ever reads that JSON — it
makes no network calls and cannot affect a tracking run.

---

## Setup

```bash
pip install -r requirements.txt
playwright install chromium        # one-time, ~150 MB; required for Maersk
```

Python 3.11 or newer.

---

## Daily use

```bash
python track_all.py bl_list.xlsx --append     # fetch from the carriers
python generate_report.py                     # build the Excel report
```

`--append` matters. The reporting layer detects delays by comparing a
container's ETA between snapshots, so **the accumulated history IS the delay
baseline**. A single run cannot show that a carrier moved its own date, and the
report will correctly report zero delays until you have two or more runs.

The report lands at `output/cargo_tracking_report.xlsx`. Close it in Excel
before re-running, or the generator exits 2 and tells you so.

## Things that will bite you

**Maersk's direct API always returns 403.** `api.maersk.com` sits behind Akamai
Bot Manager, which wants an `akamai-bm-telemetry` header generated by obfuscated
JavaScript from mouse movement and timing. It cannot be forged or replayed.
`track_all.py` therefore never calls `maersk_track.fetch` — every Maersk number
goes to one shared browser session instead. Don't "optimise" that back into a
direct call.

**The BIC prefix tells you who OWNS the box, not who is carrying it.** Leasing
prefixes (`TCLU`, `CAIU`, `TLLU`, …) say nothing about the carrier, and this
project's own data has leased boxes on MSC. `carrier_id.classify` returns a
confidence level for exactly this reason; an "unknown" means search, not fail.

**On the commercial sheet, `SHIPPING LINE` decides the carrier — not the BL
prefix.** Maersk BLs on that sheet are bare 9-digit numbers with no prefix at
all, so prefix classification cannot work on them however good the table is.

**Maersk never returns a bill of lading.** `bill_of_lading` is always null on a
Maersk row even when you searched with the real BL. Join on `tracking_number`.

**MSC returns actuals only** — no forward schedule, so `pod_eta` is often empty.
That is the carrier's API design, not missing data on your side. Last confirmed
movement is the progress signal that works for both carriers.

**Not every failure is a failure.** `errors.json` separates three cases:
`unsupported_carrier` (a real shipment on a line with no adapter),
`no_ocean_carrier` (inland/truck cargo, which never gets a bill of lading and is
finished permanently), and a genuine not-found. Only the last one is worth
investigating.

## Carrier coverage — the honest position

The **reporting layer handles all eight** target carriers: Maersk, MSC, COSCO,
CMA CGM, Hapag-Lloyd, ONE, Evergreen, Yang Ming. Carrier routing classifies all
eight from their prefixes.

The **tracking layer can fetch two**: Maersk and MSC. The other six have no
adapter, so no data is ever retrieved for them. The report says so per carrier on
its Carrier Mapping sheet rather than implying coverage that does not exist —
Hapag-Lloyd shipments on the commercial sheet are recorded as
`unsupported_carrier` and need manual tracking.

Adding an adapter means a `fetch`/`parse` pair returning the shape the two
existing adapters return, plus an entry in `ADAPTERS` in `track_all.py`. The
reporting layer needs no change beyond confirming the new carrier's event
wording — see "Add a new carrier" in [README_REPORTING.md](README_REPORTING.md).

## Known limitations

- **Maersk's consumer key rotates.** It is the key Maersk ships in its own web
  bundle. When it stops working, `maersk_debug.py` will tell you whether that is
  the cause. The browser path does not depend on it.
- **The browser path is slow** — roughly 8–15 seconds per number versus ~1 for a
  direct API call, and it breaks if Maersk restructures their frontend.
- **`msc_track.parse` labels the last event `CURRENT` regardless of what it is.**
  MSC's last event is frequently `Estimated Time of Arrival` — a forecast — so
  `current_event` and `current_date` can be future-dated. The Excel report
  detects and corrects this (it derives an explicit ACTUAL/EXPECTED basis and
  computes position from actuals only). **Anything else reading the JSON
  directly, including the Power BI model, does not.** Fixing it at source means
  changing `msc_track.parse`, which changes behaviour the Power BI model already
  depends on — deliberately left alone.
- **No scheduler.** Run it from Task Scheduler or cron. `generate_report.py`
  exits non-zero when the report is missing data it cannot account for, so a
  scheduled job can alert on that.
- **No database.** JSON files are the only store, and `--append` grows them
  without bound. They are gitignored; archive or truncate them periodically, but
  keep at least two runs so delay detection still works.
